# 知识回答历史和引用恢复

状态：开发中。Nuxt、Go、Rust 已将编码和恢复组件接入内部消息写入及历史读取；Nuxt、Go 已接入内部知识生成流程。Rust 知识生成接线、公开入口和客户端尚未实现，不能当作知识对话已可用。

知识助手消息保存在现有消息正文 CLOB 的版本化 JSON 信封中：`{"version":1,"answer":"...","sources":[{"kind":"post|comment","id":1,"version":"64位小写SHA-256"}]}`。只保存回答和被引用来源标识，不存检索到的来源正文、模型凭据或内部地址；消息角色、会话归属、模型及配置版本由现有列管理。整个编码后的 UTF-8 消息不得超过 65536 字节。信封字段须精确匹配，答案非空白且为有效 Unicode，来源 1–20 条、ID 有效、版本格式正确且同一来源不重复；未知版本、数据损坏或旧的无来源助手消息失败关闭，不直接显示。

恢复前先验证当前用户对会话的权限，再从当前业务数据按该用户重新复核所有引用的公开状态、访问权限和正文版本。任意来源不存在、撤权、删除或改动时，不返回该回答或旧引用，不将其加入模型上下文；数据库错误失败关闭。仅在全部来源通过时返回回答和来源标识，读取后仍需考虑权限变化和引用再次访问时的独立授权。恢复不能信任存储时的角色或用户声明；数据保留和删除继续遵循会话权限及级联规则。

三端内部知识助手写入在事务内锁定会话、检查序号并在写入前和提交前复核来源；普通助手写入不能写入知识会话。历史读取和最新上下文读取会检查知识助手信封及来源，并将通过的引用作为可选 `citations` 返回。失效或损坏历史当前导致整页失败；该行为仍须在三端和客户端定义稳定错误。两次查询并不锁定来源，不能证明撤权与提交竞争完全消除，真实 Oracle 并发策略仍需验证；推理期间不能持有数据库连接或锁。必须覆盖并发撤权、旧数据、分页、删除与真实 Oracle 验收。

Nuxt、Go 内部生成流程先按当前用户读取知识会话和最新消息，关闭连接后按最新用户问题检索并生成，随后通过原序号检查写入带引用的回答，保存本次模型配置快照；无证据时不写入。当前未将较早历史送入模型，完整多轮上下文需要确保所有历史引用在推理后及写入时仍有权限，不能把此阶段称为完整多轮知识对话。
