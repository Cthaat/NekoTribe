# 创建帖子评论共同需求

`POST /api/v2/posts/{id}/comments` 需要有效会话；帖子路径 ID 为规范安全正整数，响应设置 `private, no-store`，内部异常脱敏。请求体为 JSON 对象或 URL 编码表单。先验证可选 `parent_comment_id`：缺省、null 或空字符串表示根评论；否则必须是 1 至 9007199254740991 的安全整数或不带前导零的十进制字符串。随后将 `content` 按 Nuxt 字符串转换并去除首尾 JavaScript 空白，空内容返回 400。上述 ID 限制收紧原宽松解析。

通过 `fn_can_view_post` 和帖子未删除检查当前会话用户；无权查看或不存在返回 404 `帖子不存在`。获取评论序列 ID；有父评论时，仅允许同一帖子、未删除的父评论，读取其 `NVL(root_comment_id, comment_id)`，缺失返回 404 `父评论不存在`。根评论的 `root_comment_id` 使用自身新 ID，回复使用父评论的根 ID。

插入必须在同一 SQL 语句中再次检查帖子可见性、未删除状态以及父评论属于该帖且未删除；该检查受数据库语句快照影响，不能保证消除检查到提交之间的并发变化。零行时重新检查帖子，帖子不可见返回 404，否则有父评论返回 `父评论不存在`。提交后读取新评论时同样绑定用户、帖子、评论 ID 并检查可见性；无行返回 404 `评论不存在`。使用评论列表相同的作者和字段映射，`is_liked=false`、`can_delete=true`，成功消息为 `comment created`。

创建后沿用现有通知：向帖子作者发送 `comment_created` 类型的评论通知；有父评论且父作者不同于帖子作者时，另发送 `comment_reply` 通知。排除对自己的通知，沿用各接收者通知偏好和推送设置；按 Nuxt 的 160 个 UTF-16 单元压缩摘要规则生成元数据，保存通知并在允许推送时发送 `notification_created`。通知不能作为评论插入事务的一部分：评论提交后的读取、资料、通知写入或响应失败不保证回滚，多个接收者可能只处理一部分。Redis 发布失败仅降级实时推送。

Nuxt 请求体当前没有统一大小上限，Rust/Go 既有入口限制 1 MiB；三端均需对外安全报错。真实 Oracle 的自引用外键、触发器、权限竞争、CLOB、时间与序列、通知偏好/并发及 Redis 和两个客户端需要隔离环境验收。
