# 原生登录与双因素认证 v1

目标为 `POST /api/v2/auth/tokens` 及双因素挑战完成接口。Nuxt 为既有业务基准；Rust native 和 Go 独立服务分别访问共享 Oracle，不转发到 Nuxt。登录的密码验证、双因素、用户资料和新设备提醒均属于最终一致性范围；只有某一阶段可运行，不表示本功能已完成。`authentication.md` 是原始审计，具体待验收场景见 `scenarios/auth-login.json`。

## 密码与会话

登录两端先按JavaScript trim规范化账号和密码，只要求密码非空；`auth-password-input.md`的新密码6位规则不能用于登录，历史短密码继续验证。UTF-16计数和归一化的新密码样例独立记录，不改变现存bcrypt格式。

1. 公开路由读取 account/password；当前 Nuxt 的 `v2RequiredString` 对部分非字符串先转字符串再 trim，使用 email 或 username 原样匹配。无账号与密码错误均 401/40101 `账号或密码错误`；找到账号但 `is_active != 1` 或 status 非 active 时先返回 403/40301 `账号不可用`。只接受安全参数化查询，密码、哈希、令牌与密钥不得进入响应或日志。
2. 密码按平台现存 bcrypt 格式校验；Nuxt 的 bcrypt 按 UTF-8 字节在 72 字节截断，公共样例 `scenarios/auth-bcrypt.json` 固定 `$2a$`/`$2b$`、中文、长输入、错误及损坏哈希等合成情况。测试使用低成本哈希仅为快速验证，不是推荐新密码配置。不得用自行实现的加密或明文密码替代 bcrypt。
3. 密码通过后先检查双因素数据结构就绪，Nuxt 用迁移账本、当前 schema、表列/约束、索引和序列元数据只读检查；不合格返回安全 503，不在请求中自动建表/迁移。三端以 `two-factor-schema-catalog.json` 中 Nuxt 导出的只读规则与全部迁移校验值作为共同检查基础；`scenarios/two-factor-readiness.json` 包含共同字典快照和负向样例。账本不存在或存在但为空时，只要其他结构满足要求可以就绪；账本存在时任一已有记录未知或校验值不符都须拒绝，包括其他功能的记录。一次检查使用同一数据库连接，检查完成后不缓存成功结果。只在设置启用且 secret 已启用时要求第二因素；任何结构/查询异常不能绕过 2FA。
4. 未启用 2FA 或命中现有受信设备才签发会话：生成 `sess_` 加 UUID、随机 access jti 和 refresh jti、两种 JWT；Oracle 保存 access jti 和 refresh token SHA-256，而非明文 token。记录原有设备 header、IP、UA、期限，更新用户 last_login_at；返回 `{two_factor_required:false,user,tokens}`，`user` 为完整 self profile，非简化字段；头像公共地址遵循 `storage-public-urls.md`，token 和 Cookie 与 `auth-refresh.md` 契约一致。普通登录 `remember_me` 不改变 TTL。JWT 密钥及用户/session 数据必须跨端共享。
5. 密码比对成功后，直接签发会话（含已受信设备）或创建新 2FA 挑战的事务均按 user_id 锁定同一 n_users 行，再读取当前启用账号的 password_hash 与已核验版本精确比较。锁、不走缓存的读取、一次插入和提交使用同一 Oracle 连接。版本变化或账号已失效时回滚并返回 401/40101「账号或密码错误」，此请求不返回 Cookie、会话或新挑战。登录先提交时，随后完成的密码重置事务会撤销已插入的会话。Oracle 锁顺序与两个提交顺序须在真实环境验收。[Oracle 行锁文档](https://docs.oracle.com/en/database/oracle/oracle-database/19/adfns/sql-processing-for-application-developers.html)

   历史设备查询、更新 last_login、通知和读取用户资料仍保留独立边界。登录资料读取成功后才设置 Cookie；session 已提交后资料或关闭步骤失败，仍可能留下服务端会话。新设备判断依历史 fingerprint 数量（包含已撤销或过期会话）。提醒先受 login_alerts 控制；通知类型偏好决定是否存储、push 开关决定是否推送，email 开关独立决定是否发邮件，通知类型禁用并不必然阻止邮件。提醒失败不阻断登录，错误处理不能记录凭据或内部原始异常。该副作用不可省略后称为完整登录。

   三个后端在会话提交后读取当前启用账号的提醒设置和邮箱。推送读取该账号已保存的通知，通过既有 WebSocket/Redis 通道发布 `notification_created` 和 `notification_type: login_alert`。邮件复用部署的 SMTP 配置，含设备、IP 和 User-Agent，HTML 正文转义动态内容。实时投递失败后仍可继续发邮件。提醒服务日志只记录失败阶段。

## 双因素

6. 启用双因素时，密码校验后读取服务端签发的 `nekotribe_trusted_device` Cookie。在同一个 Oracle 事务中先锁定用户并重验密码版本，再按账号和凭据摘要更新未撤销且未到期的设备记录。恰好更新一行才继续插入会话，两步一并提交。设备更新为零行时回滚并走密码版本受保护的正常挑战流程。其他数据库写入错误回滚并返回安全错误。挑战使用 `2fa_` 加 UUID，300 秒到期，只返回 `{two_factor_required:true,challenge_id,account,expires_at}`。仅字面 `remember_me:true` 记录记住设备选项。客户端设备标识继续用于挑战匹配和设备提醒。
7. 挑战完成按既有路径或请求体取 challenge ID，检查账号状态和挑战期限。先解密共享 AES-256-GCM 密钥，再验证 TOTP（SHA1、6 位、30 秒、相邻时间步）或 bcrypt 恢复码，只记录匹配的恢复码 ID。共同事务锁定账号、重验所读密码哈希，依序条件消费该账号的有效挑战、可选恢复码，插入可选受信设备及会话，最后统一提交。挑战或已匹配恢复码的条件更新为零行时，回滚并返回 401/40101「双因素验证已过期，请重新登录」。写入错误回滚并返回安全错误。提交结果不确定或提交后的资料读取失败时，挑战可能已经消费。
   若请求记住已识别的设备，生成 32 字节安全随机数，编码为 `td1_` 加 64 位小写十六进制。受信设备表原 `device_fingerprint` 列保存 `td1_` 加完整凭据的 SHA-256 小写十六进制摘要，过期时间为 30 天。会话成功响应通过 HttpOnly、SameSite=Lax、Path=/ 的 Cookie 交付原凭据，Secure 沿用登录配置。
8. 保留 Nuxt 已有的非标准 JWT、TTL、用户状态、设备信任和自动提交差异及 AUTH-901..907；不以更宽输入或失败回退绕过校验。网络故障、写入提交和连接关闭结果可能未知，不能声称失败一定未写入。

9. 两种挑战完成路径都在验证 TOTP 或恢复码之前，核对密码登录创建挑战时记录的 `X-Device-Fingerprint`。客户端发送可移植的 ASCII 标识，读取时最多使用前 200 个字符。缺省或空值按 `unknown` 处理，Oracle 旧空值也按相同规则解释。标识不同返回与挑战过期相同的 401/40101，保留挑战和恢复码，不建立受信设备或签发会话。两个请求允许来自不同 IP。Nuxt Web 的本地存储不可用时，同一页面运行期使用稳定的内存标识。Flutter 沿用安全存储中的设备标识。Nuxt Web 与 Flutter Web 使用浏览器 Cookie。Flutter 原生在安全存储中按 API 基址保存凭据，仅密码登录请求携带，拒绝自动重定向。退出登录保留设备信任，重置密码或关闭双因素沿用数据库撤销规则。旧设备记录保留并在三后端统一升级后重新完成一次双因素验证。

10. 挑战完成事务按账号、双因素密钥的顺序加锁。消费挑战前重新读取密钥状态，确认仍启用且密文、IV 与认证标签同验证码核验时一致。关闭或更换密钥先提交时，本次挑战完成返回 401/40101，保留挑战和恢复码。根据是否匹配恢复码决定消费步骤，旧数据中的恢复码 ID 为零时也须条件消费。

## 验收

三端分别通过共享 bcrypt fixtures 和登录/挑战场景，验证真实 HTTP、JWT、bcrypt、TOTP 和隔离持久化边界；检查实际生产 repository 的 SQL、参数绑定和副作用顺序。三语言交叉发行/消费令牌、真实 Oracle 约束/时区/并发、通知/邮件与两前端、Windows/Linux 部署均需最终集中联测。只实现密码登录或只发挑战、不支持挑战完成，均保持 `in-progress`，不得列为 accepted。


## 客户端提交边界

Nuxt Web 与 Flutter 的密码登录和双因素完成在同一页面请求等待期间只允许一个在途提交，键盘事件与先前持有的按钮回调也不能再次调用网络层；仅禁用按钮不足以满足此要求。请求结束后允许用户主动重试，不自动重放登录或已可能消费的挑战。该守卫不提供服务端幂等性，不改变恢复码/挑战可能已消费的既有失败语义；真实并发、网络结果未知及两端三后端联调仍需验收。

客户端密码登录只检查非空账号/密码，不额外强加注册密码长度，允许已有短密码交由后端按兼容规则校验。Nuxt Web 与 Flutter 密码登录响应必须有布尔 two_factor_required；挑战必须含非空字符串 challenge_id/account 与带时区的可解析 expires_at；成功必须有正安全整数 user_id、非空 username、非空字符串 session_id/access_token/refresh_token 和两个带时区的可解析到期时间。挑战完成可省略 two_factor_required，若携带只能为 false，使用同一成功校验。不能将数字/字符串开关或缺字段转为成功。非法响应使用固定安全错误，不附带响应体、token或底层异常。

Flutter 登录仓储在保存前再次校验凭据，挑战不写令牌，保存异常向调用方传播；安全存储在全部持久化完成后才发布新内存缓存，替换时先使会话标记无效、最后写 session_id，避免顺序写入失败后读取到混合令牌。未提供的到期时间不得沿用旧记录。此规则不声称跨进程/并发写入原子性，或解决设备存储“已写入但报错”的不确定结果；这些仍须专门并发与实际设备验收，不自动重放登录。

同一 Flutter TokenStore 实例内，read/write/updateAccess/clear 按调用顺序串行化，某次操作失败不得阻断后续队列。登录与挑战完成在发起前获取会话意图版本，较新登录或退出使旧版本失效；旧响应不得写凭据或作为登录成功返回。退出发起即使旧登录失效，退出网络响应结束时仅清理仍属于本次退出版本的本地会话，不能清除此后新登录。写入中发生版本变化时，在释放操作队列前撤销该旧写入的会话标记。HTTP 自动刷新必须使用版本条件写入/清理，旧401响应与自动重试也需绑定原请求身份；晚到的受保护成功响应不得交付给已切换的会话。跨实例/跨进程与设备存储不确定结果仍需验证。

登录成功与刷新在各客户端共用纯校验模块，日期校验拒绝日历/时分秒/时区越界而非自动规范化，要求 refresh 到期晚于 access；合法时区偏移、1至9位小数秒和闰日可解析，时间比较使用微秒精度（更多位截断），避免JS毫秒精度与Dart不一致。此处不检查到期时间是否相对当前客户端时钟在未来，实际到期授权仍由后端判断。`scenarios/auth-client-response-vectors.json` 的46项共同data层样例由两端实际解码器消费，完整资料基准不代表所有非认证资料字段/默认值或HTTP envelope已一致验收。

Nuxt的会话VM仍只保留sessionId和两个到期时间，不新增可读token偏好；Pinia刷新发起时如已有本地sessionId，响应必须相同，否则不发布、不重放并仅清理原版本。无本地sessionId时不能编造旧值作比较。浏览器HttpOnly Cookie一致性与实际恢复语义仍须C3验证。

Nuxt Web 的v2登录、双因素完成、刷新和当前退出请求须在同一Nuxt app内按调用顺序发送，后一认证变更等待前一请求promise完成后才发出；不同app/SSR请求不得共享认证队列。排队前捕获app上下文和凭据输入副本，执行时恢复原上下文；失败传给原调用方且不得阻断后续队列，不自动重放。此要求只是网络顺序，JS身份版本、Pinia状态清理、普通请求重试和实际HttpOnly Cookie行为另须完整接线验收。

Nuxt Web 同一 app 的登录、挑战完成、退出在入队时同步递增会话意图版本；刷新沿用发起时的版本。登录页仅可向仍匹配的版本发布用户、令牌信息、挑战、提示和跳转。Pinia 仅为同版本共享刷新任务；旧刷新成功/失败不得更新或清空较新身份，旧任务结束不得清除新任务的忙碌标记。清理认证和重置偏好也必须使旧版本失效。默认偏好在初始化、兼容回退和重置时创建独立深拷贝，禁止通过模块级默认对象在不同 store/app 间共享用户或会话。

四个退出调用方（导航、忘记密码、修改密码、修改邮箱）共用版本受控的退出 action；凭据修改在等待期间身份已变时不得再发起退出。当前退出网络结束后，无论成功或失败均清理仍属于该操作的本地状态；旧退出不得清理新身份。结果须用明确成功/失败标记，不能用错误值的真假性判断成功，拒绝值为 null/undefined/false 仍是失败。结果发布、错误提示和延迟跳转须重新核对版本。此客户端清理不证明服务端撤销已成功，网络不确定结果仍需验收。普通受保护请求的身份、刷新后有界重试及浏览器/跨页签 Cookie 行为仍是后续完整要求。

Nuxt `apiFetch` 每次请求捕获原 app 和意图版本，在首次/重试的成功发布、错误处理、动态获取 store 后、刷新前后核对身份。过期响应以安全取消错误拒绝，不交付旧响应体/错误细节，不为新身份刷新或清理。没有 app 的请求不能借用之后出现的 app 恢复认证。401 且不属于认证入口、刷新或退出时，使用原 app 的同版本刷新，成功后至多重试原请求一次；底层 fetch retry 固定为0，禁止库或调用方额外自动重放，不用固定延迟等待。取消的请求不得重试。重试仍401时仅清理相同版本；其他状态/网络失败不新增刷新或清理。刷新失败的条件清理由 store 负责。

所有在用 Web 传输入口及全局错误兜底都必须遵守相同身份与有界恢复规则，不能将已经处理过的401再次触发刷新，也不能对无法确认原身份的旧错误发起新身份变更。`useApiFetch` 保留Nuxt响应式数据与显式refresh接口，网络执行必须绑定创建时app并委托apiFetch，内部$fetch不允许被调用方替换成绕过守卫的传输；server默认false，合法options/hooks保持可用。历史全局 `error-handler.client.ts` 没有原请求身份，退役其无条件刷新/clearError职责，不再自动注册；不通过全局异常重启认证恢复。

ofetch四种hook（onRequest/onRequestError/onResponse/onResponseError）在执行前和异步返回后都核对版本及取消状态，数组中的每个hook也分别核对。旧响应不能先进入hook再被返回值检查拦截；请求hook等待期间身份变化时不得继续发送。当前合法hook保持原执行顺序。隔离测试不证明Nuxt useFetch缓存跨账号清除、真实组件生命周期或浏览器Cookie/SSR请求转发，此类完整验收仍需执行。
