# Native backend readiness

Nuxt, Go native and Rust native expose `GET /api/ready` for deployment health checks. The endpoint has no authentication requirement and covers the Oracle and Redis connections configured for the running service. It probes Oracle and sends Redis `PING` without writing data. Both must succeed within a two-second probe budget for a `200` response with `{"status":"ready"}`. Connection failure, timeout or unavailable native configuration yields `503` with `{"status":"unavailable"}`.

Responses are JSON and carry `Cache-Control: no-store`. They report aggregate status and contain no credentials, dependency addresses or driver errors. Concurrent callers can share a probe. A driver operation that outlives the HTTP deadline must finish before another probe starts. The next probe after a failure can detect dependency recovery without restarting the process.

Use `/api/health` for process liveness. Both probe routes are exempt from Redis-backed rate limiting so readiness can enforce its deadline and liveness can respond during a Redis outage. Rust compatibility mode reports `503` at `/api/ready` because it delegates business operations to another backend. Point readiness checks for that deployment at its upstream native backend. Readiness covers dependency connectivity. Validate migrations, object storage, mail, and configured AI providers during deployment acceptance. Standalone SentimentFlow has its own deployment profile and health checks.

Readiness is visible to browser origins allowed by each native backend's existing CORS policy. Flutter endpoint settings can check the entered API origin before saving. The check uses a separate HTTP request with no account headers or cookies, refuses redirects, and times out after five seconds. A `200` needs the expected readiness JSON. Older endpoints can still be saved when the check is unsupported. Flutter Web also requires the configured browser origin and transport scheme to be allowed by the deployment.
