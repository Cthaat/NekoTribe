# 共享后端的缓存一致性

三后端可能并发写入同一 Oracle。Nuxt 的 API 响应缓存和 Oracle 查询缓存均依赖 Redis tag，Rust/Go 原生写入暂未接入这些失效事件；仅使当前用户 GET 绕过缓存不足以保护帖子、群组或其他嵌有资料的结果。完整目标是三套实现对所有被缓存的数据采用可靠的统一失效协议，并覆盖提交失败、提交后失败、Redis 不可用及多实例并发，不能通过 Redis 连接成功或尽力发送一次事件推断一致性。

在该协议完成并经过真实联测前，Nuxt 默认 `NEKO_CACHE_MODE=shared`：不读取、不写入 API 响应缓存及 Oracle 查询结果缓存，但不关闭 Redis 或其他用途。仅当共享库的所有写入均通过 Nuxt 并遵循其缓存失效路径时，可显式设置 `NEKO_CACHE_MODE=single-backend` 使用两层缓存；空值、未知值均按共享模式处理。配置在进程初始化时固定，切换部署模式需要重启全部实例。每个进程生成新的缓存标识，重启后不重用以前进程的缓存，旧条目由既有 TTL 过期。单后端模式仅属受限运行选项，开启后不能同时允许 Rust、Go 或外部写入。

该机制不改变 Oracle 隔离级别、已有在途查询或其他服务自己的缓存，也不会解决多语种后端本身尚未实现的业务。实际部署必须覆盖 Windows/Linux、多进程、Redis 重启及提交与读取时序；在有效的统一协议实现并完成验收前不得声称缓存跨后端完全一致。共享 `scenarios/cache-shared-backends.json` 为待执行验收场景，本地替身测试只证明 Nuxt 守卫行为。

即使选择单后端缓存，包含 `fn_can_view_post` 的查询也直接访问数据库，避免关注/屏蔽/可见性改变后继续使用旧权限结果；标签统计接口同时绕过响应缓存。此规则会降低相关查询的缓存命中率，不替代其他权限敏感查询的逐项审查。

单后端缓存当前采用尽力失效：Redis 在写入时故障、提交与失效之间崩溃等情形可能保留旧条目；即使所有写入经过 Nuxt 也不构成强一致保证。有严格一致性要求时保持 shared，后续需建立可恢复的失效机制并实测。

Nuxt、Go 和 Rust 对 `/api/v2` 及子路径的业务响应统一发送 `Cache-Control: private, no-store`，包括鉴权失败和未匹配路由。CORS 预检与 `/storage/` 等对象响应沿用自身缓存策略。切换后端地址后，浏览器与反向代理按该策略重新请求业务数据。

共享模式也跳过两层 Redis 缓存标签失效写入。单后端模式为每次失效和重建分配新的 Redis 标签代数。标签过期或被淘汰时，使用只在键不存在时成功的初始化，避免把仍存在的旧结果重新识别为有效。该变更处理标签淘汰，跨后端写入及提交后的可恢复失效仍待实现。

Nuxt 单后端模式的连接包装器为可识别的 DML 和 PL/SQL 累计受影响标签。连接有未提交事务时，查询直接访问 Oracle。显式提交成功后或驱动确认语句结束后事务已关闭时刷新标签，回滚成功后丢弃标签。提交报错时原错误向调用方传播，并尝试刷新标签以应对提交结果不确定的情况。该机制覆盖包装器的 `execute`、`commit` 和 `rollback`，共享库写入及提交后 Redis 故障的恢复仍待实现。
