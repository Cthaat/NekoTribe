# 帖子列表与搜索共同要求

本切片覆盖公共、热门、个人、收藏、点赞以及指定用户、标签、回复、转发的帖子列表；Nuxt `server/services/v2/posts.ts` 的 `v2ListPosts` 为现有业务来源。各入口仍需分别验证权限、查询和客户端接入。

帖子搜索以最新提交的关键词及当前视图为准。关键词清空、换页、切换账号或后端后，旧列表、错误和分页响应不得写入新视图。Flutter 动态同时清理各标签的旧列表缓存，只为当前标签重新读取。分页按帖子 ID 去重，已失效列表中的帖子操作回执不能修改新列表。浏览器和应用从现有统一接口读取当前权限对应的内容。

从搜索结果打开标签时，Nuxt Web 和 Flutter 使用 `/api/v2/tags/{name}/posts` 列出精确标签下的帖子。Nuxt Web 登录后直接打开以 `#` 开头的搜索地址也使用精确标签接口，游客继续使用公开搜索。

普通帖子详情为已登录用户提供回复帖和转发帖的切换入口，分别调用 `GET /api/v2/posts/{id}/replies` 和 `GET /api/v2/posts/{id}/retweets` 按时间升序分页。回复帖以 `reply_to_post_id` 绑定当前帖子，转发帖以 `repost_of_post_id` 绑定当前帖子。两个客户端按帖子 ID 去重，并在下一页失败时保留已读结果、重试原页。切换列表类型时从第一页读取并丢弃前一类型的迟到回执。列表分页与评论列表独立，精确评论引用页和匿名详情不调用这两个接口。账号或 Flutter 后端切换后旧回执失效。

## 身份和过滤

- GET 列表可以匿名，若带 Cookie 或 Bearer 则必须正常验证 access token 和会话；失效凭据不能降级为匿名，Cookie 优先。viewer 使用认证会话 ID，不能采用查询参数。`timeline=following` 与 `timeline=mentions` 仅登录后可用，其他 timeline 值按普通列表处理，区分大小写。
- 所有列表和总数都绑定同一 viewer，应用 `fn_can_view_post(:viewer_id,v.post_id)=1`；匿名 viewer 为数据库 NULL。`following` 额外限定 `n_user_follows` 中 viewer 关注作者且状态为 `active`，`mentions` 额外限定 viewer 被当前帖子提及。不可用客户端输入拼接 SQL。
- `q` 经 trim 和小写后，按 `%q%` 查询内容前 4000 字符、位置或标签；标签查询另外去除开头的所有 `#` 后 trim，为空则回用原 q。保持现有 Oracle LIKE 语义：`%` 和 `_` 是通配符，不做隐式转义。空 q 不加搜索过滤。搜索由参数绑定，不能把文本拼接进 SQL。
- `sort=oldest` 按创建时间升序，`popular` 按互动分降序、创建时间降序，其他值按创建时间降序；现有规则不保证相同排序键的稳定次序。不要虚构 tie-breaker 改变兼容行为。
- `trending` 允许匿名并强制 popular 排序，忽略客户端 sort；仍应用 timeline 和搜索过滤。`me`、`bookmarks`、`likes` 路由必须登录，分别限定作者是当前用户、当前用户已收藏、当前用户已点赞；不可根据查询参数选择他人。它们仍叠加 timeline、搜索及数据库可见性过滤。
- 点赞列表的默认/未知 sort 按当前用户点赞时间降序，`oldest` 按点赞时间升序，`popular` 仍按互动分排序；其他模式按帖子时间或互动分排序。查询按现有 `MAX(n_post_likes.created_at)` 取该用户的点赞时间。
- `users/{id}/posts`、`tags/{name}/posts`、`posts/{id}/replies`、`posts/{id}/retweets` 均需有效会话；分别按作者 ID、标签不区分大小写的精确名称、回复目标 ID、转发目标 ID 过滤。目标不存在时返回空列表，不自行暴露目标存在性。其余 timeline、搜索、排序及可见性条件照常叠加。标签是 URL 解码后的非空字符串，通过 SQL 绑定并在数据库中比较大小写；Nuxt 原来使用未解码的路径片段，本次修复中文及特殊字符名称的查询。
- 三条数字目标路由统一对 URL 解码后的值使用无前导零的十进制安全正整数（1..9007199254740991）。Nuxt 旧 `Number()` 解析允许科学记数法、小数和前导零；本次有意收紧以匹配帖子/用户详情，非法参数在认证后返回 400，未登录时先返回 401。

## 分页和输出

- Nuxt 使用 `v2Page`：`page` 默认 1、上限 10000，`page_size` 默认 20、上限 100；非正数或不可转为有限数采用默认。其当前 Number 解析还接受小数、科学计数法和部分数字格式，重复查询参数被当成非字符串回退。是否收紧这些边界应作为明确的三端兼容变更处理，不能偷偷只在 Rust/Go 收紧。
- 分别执行使用相同 WHERE 和参数的 COUNT 和带 `ROW_NUMBER` 的分页查询；区间是 `(page-1)*page_size+1` 到 `page*page_size`，返回 `meta={page,page_size,total,has_next}`，其中 `has_next=page*page_size<total`。两个查询并发写入时不保证一致性快照，真实 Oracle 对小数分页的行为仍需测试。
- 每个结果采用 `post-detail.md` 所定义的作者、媒体、标签、提及和 viewer_state 映射，列表读取不增加浏览量。现有 Nuxt 是对查询结果并行展开关联数据，可能多次执行媒体结构只读检查；空列表无需媒体结构检查。结构不兼容返回安全 503，其余内部异常不得泄漏数据库细节。
- 共享后端部署不得让结果缓存返回其他后端写入前的数据；目前 Nuxt 默认共享安全模式禁用结果缓存，单后端模式的 TTL 行为不作为跨后端同步方案。

## 验收边界

Nuxt Web 从账户导航打开「我的收藏」，与 Flutter 使用同一个本人收藏接口和默认排序。两端都能分页，取消收藏成功后重新读取第一页，取消失败保留当前列表。Nuxt Web 的「我的点赞」复用同一列表组件，保留点赞排序，并支持翻页。账号变化会丢弃旧列表及尚未返回的操作结果。

本人动态列表在 Nuxt Web 和 Flutter 均支持服务端搜索与最新、最早、热门排序。Flutter 提交或清除搜索、改变排序时从第一页重新读取，后续页保留已提交的搜索词和排序；账号或后端变化时作废列表。旧 Flutter 本人动态时间线入口复用此页面。

本人动态的范围筛选支持全部、公开、仅关注者、仅被提及者和私密，只筛选已加载的动态，不改变服务端页码与搜索条件。当前已加载内容没有匹配项时，Flutter 仍能读取后续页。

本人动态编辑或删除成功后，两端以当前已提交的搜索条件和排序重新读取第一页。未提交的搜索框文字不会改变刷新或翻页的查询。

Flutter 本人动态列表可直接打开发帖页；发布成功返回后以当前条件重新读取第一页，取消发布不会触发读取。

Nuxt Web 和 Flutter 的本人点赞列表都提供最新点赞、最早点赞和热门排序。Flutter 的旧点赞时间线路由使用同一列表。改变排序从第一页读起；取消点赞成功后 Flutter 重新读取当前排序的第一页，因为删除一项会移动后续页的边界。账号或后端变化会清空 Flutter 的旧列表并忽略在途结果。

`scenarios/post-list.json` 是待三端执行的共同验收清单；三端已有各自的局部隔离测试，涵盖匿名/认证过滤、分页、错误及搜索 SQL 绑定，但不是完整共同 runner，也不证明真实 Oracle LIKE、函数、排序、并发或数据库结构。URL 畸形编码和 Unicode 小写在不同运行时的边界仍需跨语言专项对照。最终须阻断 Nuxt 上游分别验证 Rust/Go，使用隔离 Oracle/Redis 和两种前端验证数据读写、搜索、权限、分页和失败响应。
