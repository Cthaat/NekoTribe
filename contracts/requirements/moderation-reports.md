# 举报提交、审核列表与状态处理

Nuxt、Go 和 Rust 使用同一个 Oracle 举报表和共享 SQL。三个接口都要求有效会话，响应使用 `Cache-Control: private, no-store`。查看队列和修改状态还要求现有审核权限。

## 提交举报

`POST /api/v2/reports` 要求 `target_type`、`target_id` 和 `reason`。支持帖子、评论、用户、群帖和群评论。ID 接受正安全整数或无前导零的十进制字符串。原因与可选优先级只接受契约列出的枚举，默认优先级为 `normal`。说明与证据链接去除两端空白，每字段最多 1000 UTF-8 字节。证据链接接收 HTTP(S) 链接和站内绝对路径。无效输入返回 400，举报自己返回 403。

帖子和评论使用正常读帖可见性规则。群帖及群评论要求有效群组、可见群内容及有效父帖。用户必须启用，且双方未拉黑。不可见、删除或不存在的目标返回同一 404。Nuxt Web 和 Flutter 的帖子及群帖入口沿用相同请求格式，Nuxt Web 会把提交绑定到发起操作的会话。

事务锁定可见目标行，再查询该举报人针对目标最新的待处理举报。原因、说明、链接和优先级完全相同时返回已有举报 ID，不增加案件计数。不同提交返回 409，已有举报全部终结后可以再提交。新举报、案件聚合和读回共用一次提交。案件计数包含历史举报，最新时间与最高优先级从实际举报计算，已有案件状态保持原值。任何写入或读回失败都回滚。

新举报聚合时，读取现有 `auto_hide_report_threshold`（保留设置键以兼容部署和客户端）。它定义内容案件提级所需的不同举报人数。只统计当前 `pending` 或 `in_review` 的举报，同一举报人最多计一次；已解决和已驳回的举报仍计入历史总量，但不计入阈值。设置为正安全整数时生效，`0`、缺失或无效值关闭自动提级。

帖子、评论、群帖和群评论的待处理或标记案件，在达到阈值时将 `low` 或 `normal` 提到 `high`，保留 `urgent`。举报用户的案件和已结案的案件不自动提级。提级只改变案件优先级，保持案件状态、负责人、内容可见性与举报原优先级。设置更改不会批量改动历史案件，仅在新的举报写入后重新计算该目标的优先级；重复提交不触发计算。

## 审核

- `GET /api/v2/moderation/reports` 按 `status`、`reason` 和 `target_type` 筛选，省略、重复传参或传 `all` 表示不限。未知单值沿用 Nuxt 的兼容默认值 `pending`、`other`、`post`。按创建时间和举报 ID 降序，越界页返回空数组及筛选后的总数。举报人和处理人只返回公开资料，缺失或停用时为 null。
- `PATCH /api/v2/moderation/reports/{report_id}` 接受正十进制安全整数 ID 和显式 `status`。允许 `pending`、`in_review`、`resolved`、`dismissed`。无效输入返回 400，举报不存在返回 404。
- 状态更新锁定举报、写入并读回再提交。终态写入解决时间，重新打开时清空解决时间。状态和处理人相同且时间字段一致时复用结果。写入或读回失败回滚。该接口更新单条举报，案件处置通过案件接口执行。

部署验收需覆盖真实 Oracle 连接间行锁、并发提交、案件聚合、时区、失败回滚、原生后端未迁移库的错误分级以及三后端与两客户端组合。
