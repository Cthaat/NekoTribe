# 帖子点赞和收藏共同需求

覆盖 `POST/DELETE /api/v2/posts/{id}/likes` 和 `POST/DELETE /api/v2/posts/{id}/bookmarks`。所有操作必须验证 access token 和会话，目标为 URL 解码后的规范正整数 ID（1..9007199254740991）。未登录先返回 401；无效 ID 返回 400；缺失、已删除或当前用户不可见的目标统一返回 404 `帖子不存在`。以前 Nuxt 允许对不可见或缺失帖子发起写入，此处有意收紧。绝不能依据客户端提供的 user_id 操作他人数据。

每次写入前通过当前用户 ID 和 `fn_can_view_post` 只读检查目标；插入/删除语句也使用同一可见性条件，避免仅凭提前检查授权。若语句影响零行，重新检查目标可见性，再区分不可见与已经处于目标状态。它仍不是严格串行化：权限可在语句提交后变化，最终需要真实 Oracle 并发、事务及隔离验收。

重复点赞/收藏和重复取消应成功返回目标状态。点赞返回 `{post_id,is_liked,likes_count}`，计数读取数据库触发器维护的 `n_post_stats`；收藏返回 `{post_id,is_bookmarked}`。首次插入点赞才产生通知，重复点赞、取消和收藏不产生点赞通知；现有 Nuxt 对本人不发送通知、对受通知偏好限制的接收者不存储/推送，其他通知行为及 Redis/WebSocket 必须按共同通知要求实现。不同实现不能因实现接口而静默丢失通知。

Nuxt Web 和 Flutter 核对回执的 `post_id` 与目标帖子一致、状态字段为布尔值，且 `likes_count` 为非负安全整数。两端使用回执更新对应状态和点赞计数。回执无效时提示操作失败。Flutter 切换帖子、账号或后端时忽略旧回执。

### 首次点赞的通知基线

- 成功插入后查找未删除帖子的作者；作者不存在或等于点赞者时不创建通知。通知接收者必须是活动用户，通知类型 `like` 的个人偏好关闭时既不存储也不推送；关闭总推送时仍存储，但不实时推送。
- 使用点赞者的 `COALESCE(display_name, username)` 作为名称，缺失时为 `有人`；通知 `type=like`、标题为“{名称} 赞了你的推文”、消息为“你的推文收到了一次点赞。”、资源类型 `post`、资源 ID 为帖子 ID、优先级 `normal`。元数据包括 `target_post_id`、`event=post_like` 和 `post_excerpt`。摘录读取仍未删除帖子的内容，折叠连续空白并去除首尾空白，按 JavaScript UTF-16 长度截取 160 单位并按需追加 `...`；缺失或空内容为 null，纯空白内容可折叠为空字符串。
- 通知存储后重新读取完整通知和接收者视角的公开 actor 资料，按 Nuxt 的 `v2MapNotification` 输出。允许推送时，消息类型为 `notification_created`，`data` 包含该通知、`notification_type=like`、发布实例的唯一 `server_id`；时间戳为毫秒。跨实例通过 Redis `ws:user:{接收者ID}` 频道发送，WebSocket 连接实例向该用户投递，须防止本实例的 Redis 回声重复投递。字段不能只发通知 ID 或省略 actor 而声称与现有客户端一致。
- 当前 Nuxt 在点赞、计数读取、通知插入和推送间不提供单事务保证；通知插入与映射错误可能在点赞已提交后返回错误，Redis 不可用时降级且不保证实时送达。原生实现要明确记录同样的失败边界并进行故障测试；未来增强可靠性需另行定义跨三端一致的重试与去重，不得把重试结果当成新点赞再次通知。

Nuxt 现有写入单独自动提交，随后读取计数及创建通知；后续失败可能导致写入已成功但响应为 500，不承诺跨写入与通知的原子回滚。并发首次插入的唯一约束冲突处理、会话取消、消息事件一致性和故障恢复需定义并测试；不得将数据库替身作为真实并发证明。接口异常安全收口，变更需执行适当缓存失效或保持共享安全缓存模式。

三端须独立实现此需求和共同场景，真实 Oracle 触发器、并发、通知持久化和实时投递、跨后端切换及双前端需最后隔离联测。本文件当前记录开发目标，不表示 Rust/Go 已完成或任何通知路径已验收。
