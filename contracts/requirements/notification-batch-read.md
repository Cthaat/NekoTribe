# 批量通知状态共同需求

`PUT /api/v2/notifications/read-status` 需要有效会话，只能修改当前用户的通知。支持对象请求体和 `is_read` 的单条通知相同布尔转换；省略 `is_read` 按兼容行为设置未读。

`notification_ids` 缺省或为空数组时更新该用户全部未删除通知；非空数组指定要更新的通知，并包括已删除的自身通知。数组最多 1000 项，每项必须为 1 到 9007199254740991 的 JSON 安全正整数；null、字符串、非数组或任一无效元素统一返回 400，不能退化为全部更新。此校验收紧旧 Nuxt 对无效值的过滤行为，防止错误输入意外更新全部通知。重复 ID 按顺序重复执行并计入每次受影响行数，以兼容原有逻辑。被指定的不存在或他人通知不计数、不报 404。

所有写入绑定会话用户。全部模式以单条 SQL 更新；指定模式按顺序逐项自动提交，任何后续失败不能回滚先前更新，失败时不发布事件。成功返回 `{updated_count}`，并向该用户发布 `notifications_read_status_updated`，事件数据为全部模式 `{all:true,is_read,updated_count}`，或指定模式 `{notification_ids,is_read,updated_count}`。Redis 发布失败只降级实时投递。响应及错误应禁止共享缓存，内部异常脱敏。

客户端的“标记已读”必须显式传入 `is_read:true`；针对空选中列表的客户端批量操作应本地无操作，全部已读需显式调用。真实 Oracle 并发、每项提交后的部分失败、Redis 和两客户端仍需隔离环境验收。

Nuxt Web 和 Flutter 提供独立的列表内已读操作。该操作只提交当前筛选下已加载的未读通知 ID，Nuxt Web 同时应用列表搜索条件。回收站和没有可操作通知的列表不发送请求。列表超过 1000 个 ID 时按批提交，切换账号或后端时停止余下批次。任一批失败后刷新列表，以反映可能已经提交的写入。
