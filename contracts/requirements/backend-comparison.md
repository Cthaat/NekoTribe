# Native backend comparison

Use the same fixture snapshot, schema revision, backend configuration and upstream model stub for each isolated backend. Replays consume the shared executable [cases](../scenarios/backend-comparison.json) in order. For each operation record actual HTTP status, normalized JSON and the result of the applicable read-only Oracle assertion. Compare Nuxt, Go and Rust to the same contract outcome and to each other. Report a missing observation, a status mismatch, a response mismatch or a failed database assertion as a difference. Status and body shape, nullability, ordered lists, booleans and counts remain significant.

Map captured identities to fixture symbols. Normalize dates only in timestamp fields, using a stable timestamp marker for valid timestamps. Redact access and refresh tokens, passwords and credentials before any output. Run isolated stateful cases with fixture accounts only. Use separate cloned application schemas so all targets can start from the same rows. Each benchmark targets one backend at a time and should use the same workload counts, concurrency, fixture snapshot, hardware limits and service startup procedure.

The benchmark workload includes feed and public profile reads, post creation and likes, session refresh, authenticated WebSocket receipt of a channel message sent by HTTP, and writing generation through the configured AI adapter. Measure from request dispatch to response consumption, and from channel message send to matching WebSocket receipt. Report successful operations per second, latency P50/P95/P99, error and sample counts, ready startup time and resident process memory. Report missing measurements explicitly. Reports are an offline tool deliverable until three isolated, equivalent live targets have been run.
