# AI-MODEL-SWITCHING：模型可替换要求

版本：17。三个产品方向支持模型替换，包括知识问答与写作、群运营 Agent、审核辅助。首期检索数据为公开帖子、评论和平台规则。

本文件定义模型切换行为。Qwen 是候选模型，业务层通过通用推理适配器接入模型。真实能力和完整切换场景按下文验收。

## 行为要求

| ID | 必须满足的行为 |
| --- | --- |
| MODEL-001 | 业务以用途选择模型：知识问答、写作、Agent、审核可各自配置；向量化/重排分别配置。业务层不写死品牌、模型名称、模型文件位置、主机地址或端口。 |
| MODEL-002 | 模型注册包含自定义标识、提供方/适配器、服务地址、真实 model ID、明确的模型版本、凭据引用及能力。凭据由服务端保管，不进入前端、需求样例、日志或普通接口响应。 |
| MODEL-003 | 更换同协议模型通过配置完成，不改业务代码/两套前端/公共业务接口。Ollama、本地或远程 OpenAI 兼容服务由适配器隔离；新的不兼容协议需要新增适配器，不能承诺任意私有 API 零代码接入。 |
| MODEL-004 | 配置生效后新请求读取新选择，单次请求固定模型/参数/配置版本直至完成；切换不得使在途流式输出混用模型。记录每轮实际使用的模型，不悄悄更改已有对话内容或已生成草稿。 |
| MODEL-005 | 模型注册/启用有能力核对：工具调用、结构化结果、图片输入、上下文和输出限制。Agent/审核等功能在能力不足时明确拒绝或提示配置问题，不把虚构工具结果或无效 JSON 当成功；不默认静默换模型。 |
| MODEL-006 | 访问失败、超时、取消和资源限制使用一致业务错误，不泄漏密钥/内部地址。回退只有在明确配置及允许的数据范围内发生，记录实际模型；不能在本地失败后未经配置把内容送往外部服务。 |
| MODEL-007 | 对话模型与向量模型独立生命周期。只换对话模型一般不重建索引；向量模型/版本/分块规则变化需新索引和重建，即使维度相同也不能混用旧向量。新索引完成校验后切换，保留明确回退方式；维度不符必须拒绝。 |
| MODEL-008 | 三后端使用同一需求、配置语义和场景；Rust/Go 不借 Nuxt 路由完成切换。共享推理服务不等于共享 Nuxt 业务进程；前端只调用统一业务接口。 |
| MODEL-009 | 公开内容范围不因切模型、Agent 工具或索引回退而扩大。检索结果按平台权限校验，删除/撤回/权限变化同步失效；公开内容仍作为资料，不能作为改变系统指令/权限的可信来源。 |

## 验收

共同场景位于 `specifications/scenarios/ai-model-switching.json`。每个后端需分别记录实现提交、配置/模型版本、实际请求目标、流式/错误结果及必要索引证据。当前场景全部 `not-run`，没有实际模型通过记录。

固定两个兼容模型做 A→B→A 切换，验证真实请求的 model 字段/目标服务变化，而非只改界面名称；再验证不兼容能力、在途请求固定、超时、凭据隔离和索引模型变化。不同协议的适配器各自通过相同业务断言。模型不可在硬件上运行时明确报告资源条件，不将“允许填 model ID”称为可用。

## 部署文件热切换

三套后端启动时读取可选的 `AI_MODEL_CONFIG_FILE`，指向部署人员管理的普通 JSON 文件。文件使用 UTF-8 无 BOM，最大 64 KiB，格式沿用 `ai-model-configuration.md`，`revision` 上限为 `999999999999999`。配置该路径后，四个用途均以该文件为准。未配置路径时，继续从 `AI_MODEL_CONFIG_JSON` 读取配置。

进程在收到模型选择请求时检查文件，任意一秒内最多读取一次。配置整体校验成功且版本严格增加后才发布。文件删除、暂时不可读、格式错误及同版或旧版文件都会保留当前进程最近一次有效版本。进程尚未加载有效版本时，受影响的 AI 业务返回现有不可用响应。版本记录存在进程内，重启后从磁盘开始。

在文件所在目录先写临时文件，再以同目录原子替换方式发布。回退模型需复制旧绑定并递增 `revision`。容器部署应将配置所在目录只读挂载到容器，并将 `AI_MODEL_CONFIG_FILE` 设置为容器内路径，这样宿主机替换文件后容器能看到新文件。文件只引用密钥环境变量名，变更进程注入的密钥仍需重启。各实例独立读取文件，切换完成后可以从生成记录的模型及配置版本确认生效。

Nuxt 工作树的共享发布命令支持预检和原子发布。发布时须提供预期当前版本，仅首次发布允许预期版本为 0。候选无效、当前版本与预期不符、候选版本未递增或有另一发布占用锁时，命令失败并保留当前文件。三套后端的 Compose 覆盖配置使用同一个目录变量 `NEKO_AI_MODEL_CONFIG_DIR`，只读挂载包含 `model.json` 的目录。

`bind <active> <expected-revision> <role> <profile> [<role> <profile> ...]` 在同一发布锁内将一个或多个用途切换到已登记的模型。每个用途只可指定一次。完整配置通过校验后以一个递增版本发布。所有绑定都相同时保持原版本。`rollback <previous> <active> <expected-revision>` 读取保留的旧配置，使用当前版本加一重新发布。两种操作均要求已有有效版本，且失败时保留当前配置。开发和运维可在发布前用 `probe` 验证模型实际能力。

共享发布工具在替换生效文件前，将当前有效配置原子归档为 `<active>.history/<revision>.json`。重复发布可复用内容完全相同的归档，遇到同版本不同内容或归档失败则终止发布。首次发布和相同绑定的空操作不产生归档。`rollback-last <active> <expected-revision>` 在同一发布锁内选择低于当前版本的最新归档，校验后使用当前版本加一发布。找不到归档或归档无效时保留当前文件。归档沿用部署配置目录的访问边界，跨机需要共同分发配置时可同时复制归档目录。密钥仍来自本机环境，归档只保留原配置。

登录后可通过 `GET /api/v2/ai/availability` 查看该实例当前加载的 `model_config_revision`。该字段和用途可用状态来自同一份配置快照。没有有效配置时版本为 `null`，旧版后端可能省略字段。已加载的版本可在用途关闭或缺少模型服务凭据时独立查询，查询不发起推理。发布或回退后可用 `verify-active <expected-revision> <backend-base>...` 检查每个实例，发现版本不符或无法确认即返回非零退出码。

在地址之后添加 `--wait-ms` 和 1～60000 毫秒的整数，可在有限时间内等待所有实例完成加载。每轮并行检查全部目标，只有同一轮均返回目标版本才成功。旧版本、尚未加载配置或暂时不可用允许重试。发现更高版本或明确不支持版本状态的实例时提前结束。未传该参数时仅查询一轮。

`verify-active` 可附加 `--require-ready knowledge,writing,agent,moderation` 以核对一个或多个用途。逗号分隔的角色不得重复，`agent` 对应状态中的 `inference.group`。每个目标均须在同一轮返回预期版本且所选用途为 `true`。未就绪报告 `INFERENCE_UNAVAILABLE` 和对应角色，可在等待窗口内重试；缺少有效布尔状态报告 `STATUS_UNSUPPORTED`。省略时沿用只核对版本的行为。配置就绪依据现有状态接口，不发起推理。

Nuxt Web 和 Flutter 的问答、写作、群运营和审核入口显示当前后端的有效配置版本，与历史回复自身的模型版本分开。两端仅接受 1～999999999999999 的整数版本，省略或为 `null` 时隐藏版本。刷新、读取失败、切换账号或目标，以及 Flutter 切换后端时清除旧值。重新读取后展示当前实例的版本，无需生成消息。

部署人员可额外执行 `probe`，对候选配置的四个用途逐项发起真实推理。问答须从一条合成群帖返回正确答案和有效的结构化引用；写作检查普通文本生成。群运营使用正式的 `public_search` 工具定义，检查模型按指定检索词发出一次调用，并根据模拟结果续写。审核检查返回内容是否符合探测 JSON 结构。探测仅发送固定合成内容，报告只含配置版本、用途和结果码。探测不发布配置，离线预检和发布仍可独立运行。四个用途的探测通过后仍需在目标后端验收业务调用及实时切换。

`publish-checked <candidate> <active> <expected-revision>` 读取候选一次，记录当前文件并核对版本后执行同一套四用途探测。探测全通过后才获取发布锁，复核当前文件的版本与原字节，再原子发布已探测的候选字节。任一探测失败、目标内容在探测期间改变或发布锁被占用时，命令失败并保留当前配置。预期版本为 0 时，探测前和发布锁内都要求目标文件尚未存在。

独立运行 `probe <configuration> --roles knowledge,writing,agent,moderation` 时，可指定一个或多个不重复的角色，按参数顺序执行并且只报告所选角色。角色名单空项、重复或未知时，在推理前拒绝。候选配置本身仍整体校验。正式发布及带探测的回退仍验证四个用途。

`list <configuration>` 输出当前版本、四个用途的绑定、已登记的配置 ID、公开版本标签和能力声明。输出省略服务地址和密钥环境变量名。`bind-checked` 接收与 `bind` 相同的参数，只探测实际变更的用途。所有探测通过后在发布锁内确认当前文件仍是原字节，再原子发布。任一探测失败时保留全部原绑定。全部绑定相同时直接返回原版本。

`diff <active> <candidate>` 离线校验两份配置并比较四个用途实际选中的模型。输出两份配置版本、各用途前后的模型配置 ID 与变化字段名。能力按集合比较，纯版本递增和能力顺序变化不算用途变化。报告限于当前绑定，未绑定的模型通过 `list` 查看。该命令不发起推理或替换文件。

`rollback-last-checked <active> <expected-revision>` 读取最近一份归档。`rollback-checked <previous> <active> <expected-revision>` 可指定一份配置文件，其版本必须低于当前版本。两条命令都将选定配置重编号为当前版本加一，再探测四个用途。任一探测失败时保留当前配置及归档。探测全部通过后，工具在发布锁内核对当前文件的版本与原字节，再发布同一候选。回退报告仅包含版本、用途和探测结果。

在模型配置中填写可公开的 `modelVersion` 标签，可以区分仍使用同一提供方 model 名称的不同构建、权重或量化版本。四类生成在提交回复时，把本轮快照中的模型配置 ID、版本标签和配置代数写入会话记录。版本标签缺省时保留为 null，旧消息保留原始记录。标签由部署者登记，真实提供方版本仍需在配置发布和验收时核对。

Nuxt Web 和 Flutter 在助手结果旁显示该消息自己的 `model_version`。字段缺失、为空或不符合模型标签格式时继续显示历史结果。群运营草稿和审核建议失效时沿用原本的隐藏规则，不为失效内容显示版本标签。客户端从已保存的消息读取标签，切换当前模型不会重写历史标签。

两个客户端在同一位置显示该条可见助手结果保存的 `config_revision`，与入口显示的当前版本分别标注。仅显示 1～999999999999999 的整数。字段缺失、值无效、消息由用户发送，或结果不再可见时，隐藏该项。
