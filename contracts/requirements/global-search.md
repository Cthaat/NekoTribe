# Global search (B1.1, revision 1)

All paths below start with /api/v2. Success uses the v2 envelope (code 200). Existing post, user, group and tag list routes retain their page/page_size semantics. Single-conversation chat and AI knowledge retrieval keep their own search scopes.

## Input and viewer

GET /search and /search/suggestions require q. Decode UTF-8, trim Unicode White_Space, normalize NFC, then require 1–100 Unicode scalar values. The display query is this normalized text. The matching and history key additionally folds ASCII A–Z to a–z. Other code points remain literal. Treat %, _ and backslash as text; escape all three for SQL LIKE and bind the value. Reject malformed UTF-8, repeated or unknown query parameters, unsupported enums, blank values, and invalid decimal integers with 400/40001. Limit is 1–50 inclusive, default 20. A missing credential allows guest reads of search, suggestions and trending; a supplied invalid credential returns 401. A forbidden account returns 403. Both history operations require login. User identity comes exclusively from the verified session. Send Cache-Control: private, no-store on personalized responses.

Apply visibility **before** ranking, aggregation, counts, highlights, pagination and suggestions. Reuse post-list, user-discovery, group-lists and tag-list requirements, including deletion, bans, bidirectional blocks, mutes and private-group membership or post visibility. A tag derived solely from hidden posts cannot surface. Anonymous reads use only public sources. Apply visibility anew on every request and keep caches isolated by viewer and visibility changes. Never use a secret match to produce a public hint.

## Results, ordering and cursors

GET /search selects type=all (default), posts, users, groups or tags. Match a literal substring of the NFC post body, username/display name, group name or tag name respectively. Emit one hit per (type,id). Post, user and group IDs are canonical decimal strings; a tag ID is its canonical tag name without a leading hash. Label is the visible matched field, plain text; for multiple user fields choose best match class then username before display name. No HTML markup. Highlights are all left-to-right non-overlapping [start,end) ranges in Unicode scalars of that label, after NFC and before ASCII folding.

Apply one limit across all sections. Global order is type in posts/users/groups/tags order, then match class (exact, prefix, substring), then numeric ID ascending or for tags binary UTF-8 ID ascending. Scan the ordered hits after the last key and group the returned slice into four arrays. Counts are exact visible unique hit counts before cursor/limit for the selected types, zero for unselected types. All four keys always exist in sections and counts. Return null next_cursor on the last page (including empty). Tied class and tab boundaries use the same keyset rule. Stable data yields no duplicate or missing hit; live edits and visibility changes can change totals between requests. Never treat a cursor as an authorization grant.

meta contains limit and next_cursor for search and history; suggestions, trending and DELETE set meta to null. Cursor is opaque to clients, integrity protected and portable across the three servers. Use base64url without padding of a compact UTF-8 JSON array, a period, then base64url HMAC-SHA256 over the ASCII first segment with the shared deployment search cursor secret. Array fields in order: version 1, resource ("search" or "history"), viewer (decimal user ID or "guest"), normalized query (empty for history), type ("all" for history), limit, last key. Search key is [type,matchClass,id] with numeric class 0/1/2; history key is [updated_at,normalized_query]. Verify MAC before interpretation; compare every binding and validate last-key shape. Invalid, modified, foreign, wrong-resource, or incompatible cursors return 400 without writes. Accept at most 2048 encoded characters. All backends consume the issuer’s exact encoded bytes.

## Suggestions, trends and history

GET /search/suggestions returns distinct visible labels whose normalized key starts with q, ordered exact first then binary normalized label ascending. For equal keys return the binary-smallest eligible NFC display spelling. No history or trend side effects.

GET /search/trending uses a rolling UTC Redis window (24h default, 7d alternative), accepting events with now-window < time <= now. Count one event per successfully completed first-page search whose term matches a then-public, anonymously visible source label. Use the normalized term and public source identity, never account IDs or private history as public output. Re-evaluate public and caller visibility for event sources before counting. Attribute each event to the first eligible public hit in the public search order; omit the event if that source no longer supports the literal term. Return positive counts only, sorted count descending then binary UTF-8 term ascending. Redis failure on trending yields sanitized 503; a failed best-effort trend event does not fail search. Neither a continuation, suggestion nor a rejected request records an event.

A valid authenticated GET /search first page (including zero hits) atomically upserts (user_id,normalized_query) with latest display query and an explicit UTC update time before reporting success. A duplicate submission updates one row. Continuations and anonymous searches never write history. GET /users/me/search-history orders updated_at DESC then normalized_query binary ASC, serialized as UTC RFC3339 with six fractional digits. DELETE accepts exactly q (same normalization) or clear=true. Both target only the viewer; idempotent success returns affected rows in data.deleted. Missing selector, combining selectors or attempting to pass user_id returns 400. No default bulk delete.

Missing/incompatible history storage returns sanitized 503/50301 on history GET/DELETE and authenticated first-page search, before reporting success or emitting a trend event. Anonymous search, continuations, suggestions and trending do not require that table. A B0.1 tier rejection precedes business reads/writes, returns the registered 42901 transport and quota headers. History DELETE belongs to Write; all four GET operations belong to Read. Required structures are checked read-only. Explicit Oracle migration adds the history table, unique owner/term index and owner/update-time DESC index; operations never issue DDL.
