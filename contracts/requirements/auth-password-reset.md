# 密码重置的共同事务行为

`POST /api/v2/auth/password-reset` 是公开接口，三后端独立执行同一流程，不能依赖另一个后端进程。版本 2 修复重放和既有会话未撤销的问题；真实 Oracle 并发验收仍未完成。

1. 按顺序读取 `email`、`verification_id`、`code`、`new_password`；按 v2 标量字符串规则转换并去除首尾空白，任意字段为空返回 400 `<字段> 不能为空`。支持现有 JSON 和表单输入。
2. 直接按邮箱、用途 `password_reset`、验证码标识查尚未过期的 OTP，不要求先访问独立验证码校验接口。无记录返回 400 `验证码不存在或已过期`；bcrypt 不匹配返回 401 `验证码错误`。随后用 bcrypt 成本 10 生成新密码哈希，按 Nuxt 的 UTF-8 前 72 字节计算。
3. 在同一数据库事务中，按邮箱、用途、标识、查到的原验证码哈希和过期时间条件更新 OTP；同时写入 `verified_at`、过期时间和不可验证的 `!consumed!` 哈希标记。更新零行返回 400；多行视为数据库异常。条件更新旨在让同一验证码的并发请求只有一个成功，但真实 Oracle 行为仍需实测。
4. 同一事务按邮箱绑定参数更新唯一用户密码，零行返回 404 `用户不存在`，多行按数据库异常处理；再撤销该用户当时已存在且未撤销的会话，然后提交。任一步失败时回滚，不能保留部分成功的验证码消费或密码更新。提交或连接关闭异常可能使客户端无法确定实际提交结果，不能承诺一定未提交。
5. 成功返回 `{code:200,message:"password reset success",data:null,meta:null}`，不设置 Cookie；错误安全返回，不得把密码、验证码、内部异常或连接信息输出到响应与日志。
6. 本步骤不保证阻止验证旧密码后、事务提交期间才创建的新会话；既有 WebSocket 连接、已发出的双因素挑战和受信设备也未在此处强制断开或清除。需要在登录/挑战发放与实时连接中设计一致的撤销机制；限流、密码强度和统一错误信息策略也尚未完成。

`scenarios/auth-password-reset.json` 保存合成的隔离用例，覆盖校验顺序、不同 OTP 状态、事务失败及提交后副作用。真实 Oracle、并发、会话安全、跨后端登录和 Windows/Linux 跨机器部署必须另行验收。
