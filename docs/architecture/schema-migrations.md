# Explicit schema migrations (T13)

自 T13 起，功能数据库结构的定义、检查与增量升级统一收拢到数据库层（最初覆盖 5 组特性结构，现已随后续版本在 `server/database/schema-definition.mjs` 中扩展至 **19 组共 64 个迁移步骤**，完整清单以 `node scripts/migrate-db.mjs --plan` 实测为准）。默认只打印离线计划；只有显式 `--check` / `--apply` 才连接目标，`--dotenv` 用于选择私有环境文件。业务请求不再执行结构变更，缺少结构时返回通用 503。下面记录核心不变量、权限与恢复边界。

The schema definitions in `server/database/schema-definition.mjs` are the authority for the incremental feature schemas (originally the five formerly request-created schemas in T13, now expanded to 19 feature groups / 64 steps). The database engine and HTTP readiness adapter consume those same definitions. The full SQL baseline remains a new-environment bootstrap, never an upgrade script; a static test keeps its feature objects aligned with this authority.

`node scripts/migrate-db.mjs` prints an offline plan and never loads credentials or a database driver. `--check` explicitly connects for read-only inspection. `--apply` explicitly connects and applies missing feature objects and missing global settings under an Oracle session lock. Credentials are read from environment or `.env`, never command-line arguments or diagnostic output.

Business requests only inspect feature readiness. Missing or incompatible schema returns a sanitized 503; ordinary user-specific business writes remain in services. Requests never create/alter/drop schema objects or insert global migration seeds.

Existing columns, indexes and constraints are inspected semantically rather than trusted by name. Existing sequences are never reset, existing settings are never overwritten, and business tables are never dropped or reset. Incompatible columns or unrelated constraints require operator intervention. A legacy moderation target constraint is replaced only when its definition is a known subset of the required definition: validate a temporary replacement before dropping the old constraint, then rename. Lock and Oracle errors stop execution rather than being ignored.

Oracle DDL implicitly commits. The tool therefore verifies and records each immutable migration step separately, checks recorded checksums before work, stops on failure without marking that step successful, and re-inspects the database on retry. A partially completed constraint replacement is recoverable. It does not promise transactional rollback. One DBMS_LOCK session lock spans DDL commits; executing it requires an explicit administrator grant. Read-only checks and application readiness do not acquire that lock or write a migration ledger.

Run `node scripts/migrate-db.mjs --plan`, then `--check` or `--apply` explicitly. Connected commands use `NUXT_ORACLE_*` configuration in preference to equivalent `ORACLE_*` values; existing process environment overrides `.env`. Connect as the target schema owner: switching only `CURRENT_SCHEMA` is rejected. No password flags are supported. The existing full-baseline initializer remains separate; an existing database must never be upgraded by replaying that baseline.

Select an isolated configuration explicitly with `node scripts/migrate-db.mjs --check --dotenv .env.test` and then `--apply --dotenv .env.test`. Paths resolve relative to the project root, matching the application launcher. An explicitly requested missing file fails before loading the driver; process environment still takes precedence. Without `--dotenv`, `.env` is optional so containers can supply configuration exclusively through their environment. Only one action and one dotenv path are accepted; even `--plan --dotenv .env.test` does not read that file, environment values or the driver. Secrets belong inside the selected configuration, never command-line arguments.

For portable production output, preserve `scripts/migrate-db.mjs` and the `server/database/*.mjs` files alongside `.output/`. The connected command first resolves the normal source dependency and otherwise resolves `oracledb` beside `.output/server/index.mjs`. Plan mode resolves neither driver. Do not copy platform-specific native Oracle dependencies between incompatible operating systems/architectures.

An administrator must authorize a migration account to execute `SYS.DBMS_LOCK`; the tool never grants privileges or falls back to an unlocked/row-locked migration. For the isolated development schema only, an administrator may deliberately execute `GRANT EXECUTE ON SYS.DBMS_LOCK TO NEKO_APP`. Object creation must occur as the intended schema owner, and that identity needs the required table/sequence/index/constraint privileges. There is no automatic privilege escalation. This iteration deliberately requires `USER = CURRENT_SCHEMA` for both readiness and migration: it supports the existing schema-owner connection model, not a separately named application login with cross-owner metadata access. Runtime code executes only dictionary reads and ordinary business DML; that is not a claim that the owner's database privileges have been reduced. A separate least-privilege login needs an explicit owner-aware query/pool design and its own acceptance work.

The baseline and authority currently have identical required column types, nullability and defaults. Constraint names, sequence caching and tablespaces are deliberately not identity checks; key column order, foreign targets/delete rules, enabled/validated constraint predicates, index columns/order and sequence increment/cycle behavior are checked. Existing administrator-edited setting values and labels are accepted; setting value types must remain compatible. Compatibility exceptions must be explicit, reviewed and tested, rather than broad type/default coercion. Readiness has no global cache, so a new schema/connection or later drift cannot inherit an earlier ready flag. Product responses say only that the service is temporarily unavailable; the feature and migration-check action remain server diagnostics.

Concurrent checks of the same feature on one live connection share only their in-flight promise (for example, mapping a page of posts). Success and failure both discard that promise immediately. Subsequent calls, other features and other connections still inspect their own current schema; there is no cached ready result or time-based permission bypass.

The static implementation tests alone do not establish real database acceptance. The 2026-10-26 runtime audit records subsequent Oracle Free 23.26.3 tests, including a real implicit NOT NULL metadata difference and its repair. Those results do not establish Oracle 19c or arbitrary cross-owner least-privilege compatibility. Before changing production privileges or deploying, verify against the actual target version, data and account model.
