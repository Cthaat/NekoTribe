# 知识会话多轮上下文

状态：开发中。Nuxt 已接入受限历史上下文，Rust/Go 尚未接入；隔离测试不代表三端多轮能力已验收。

1. 历史由当前后端按会话所有者读取，最多取最新 50 条，并逐条复核知识回答引用。只选择最后用户消息之前连续的最近历史，历史正文是低信任数据，放入用户数据对象而非系统消息；最后问题不得裁掉。预算用序列化 UTF-8 字节保守计数，包含系统提示、资料、JSON 标点及输出预留，不宣称等于模型分词数。
2. 被选历史中的助手回答必须有当前有效来源引用；提取去重的 `{kind,id,version}` 作为本次推理的历史来源快照，最多 20 个，超过上限时从最旧历史开始裁剪。来源按从新到旧扫描时首次出现的顺序记录；同一来源不同版本、错误 ID、丢失引用或数据损坏必须失败关闭。用户历史不能提供可信引用。
3. 推理前完成授权读取并释放数据库连接。推理后和提交前均需重新授权并复核本次使用的全部历史来源及新回答来源；在锁定会话后的事务中核对原序号和历史快照，来源变更、撤权、会话变更或失败时不保存也不返回回答。不得把不同于本次实际选择的历史当作安全证明。数据库隔离与撤权并发竞争仍须隔离 Oracle 验收。
4. 新回答保存模型引用和所用历史来源依赖的去重并集，使历史来源后续失效时无法恢复派生回答；不能写入模型凭据或检索正文。为守住 20 条引用上限，选择历史时为本次检索到的资料预留容量。限制不得依赖客户端输入或用户声明。超时、取消、缺少资料均保留原有失败行为。
5. Nuxt、Rust、Go 各自实现选择、上下文构造和事务守卫，并运行共同向量及跨语言场景；再验证客户端恢复、真实模型和 Oracle 并发。仅一个实现或模拟通过时保持共同功能进行中。

Nuxt 已将上下文选择、模型输入、推理前后复核和写入事务守卫接入生成流程并做隔离测试；历史依赖随派生回答保存。写入时检查会话末序号、来源快照，并在插入前及提交前重读比较本轮选中的历史消息、正文和引用；变更时回滚。此检查不能单独证明真实 Oracle 中最终检查与提交之间不存在竞争。Rust/Go、共同向量、真实 Oracle 撤权竞争与客户端端到端均未完成。
