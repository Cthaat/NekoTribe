# 改邮箱客户端响应与401语义计划

继续已授权的接口对齐，不新增产品决策。现状：Nuxt泛型类型不校验运行时响应，Flutter将成功data直接丢弃；验证码错误401还会触发通用刷新/重放/清理，违反失败不退出规则。

1. 先写共同响应向量及两端实际API回归，覆盖完整success envelope、email与捕获请求一致、有效带时区日历时间、缺字段/类型/业务错误/未知附加字段。再写401不重放/不清会话的失败回归。
2. Nuxt复用现有严格时间算法（移入无业务依赖工具，认证原错误语义不变）；改邮箱API验证原始envelope再返回DTO。Flutter增加可选success-envelope验证钩子并在该API使用，强类型data解码复用现有时间解析器。
3. 两端对改邮箱401保留鉴权发送和会话归属检查，但不自动刷新/重放或清理；其他普通资源保留既有有界恢复。用户可在明确结果后主动操作。
4. 运行相关API/认证/安全页回归、typecheck/analyze及contracts/parity；同步需求、场景与接手记录。不启动Docker或真实服务。

本步不等于所有账号输入已统一；邮箱格式、密码长度与Unicode trim规则须基于现有三后端规则继续核对，不擅自新增密码策略。真实Cookie/浏览器/设备存储/网络与六组合留待集中验收。
