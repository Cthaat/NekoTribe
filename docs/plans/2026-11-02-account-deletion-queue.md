# 注销请求与认证 Cookie 顺序

在已授权的静态开发范围内接续安全页生命周期工作。空间复核已确认约99 GiB可用，历史92.60 GiB回收有效，本次不再删除数据。

设计：复用每Nuxt app独立的认证队列，让注销与登录、2FA登录完成、刷新、退出按响应顺序执行。注销捕获提交参数与app，执行前和完成后都核对发起版本；队列等待期间身份变化则取消，不能用后来的Cookie注销另一会话。若登录/退出等身份变更已经排队或执行中，新注销立即取消。普通刷新不改变身份，仍允许其完成后执行注销。不通过全局锁串行不同SSR用户。

- [x] 先写隔离回归，复现注销响应晚到覆盖新登录Cookie、等待期间身份变化、身份变更在途、参数快照和跨app隔离。
- [x] 抽取现有认证调度函数并增加会话归属调度，复用传输层取消语义；仅注销使用新调度，保留普通资料请求和业务401策略。
- [x] 运行实际传输/Pinia/服务集成与相关认证回归、typecheck、contracts/parity；同步共同需求与接手入口。

测试中的Cookie罐仅用于观察响应顺序，不等价真实浏览器HttpOnly/SSR部署验收。完整凭据envelope/2FA字段解码、已显示秘密失效及AUTH-905后端会话发放竞态继续保留。
