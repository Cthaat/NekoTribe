# 三套独立后端功能一致与持续同步计划

状态：需求范围已确认，当前交付为需求基线和分阶段开发计划；尚未完成 Rust/Go 原生业务。原目录整理与兼容联调的结果继续保留，不作为本计划的完成证明。

更新：用户要求用大模型/Agent 替换旧情感分析功能，并明确选择保留独立 Python 服务作为三后端共享服务。退役旧情感分析接口不等于删除 Python 服务、源码或模型数据；三后端须统一接入、鉴权和错误处理。知识问答与写作、群运营 Agent、审核辅助全部纳入，首期只使用公开帖子/评论/平台规则，模型必须可配置切换。三后端完整独立与持续同步要求不变。

## 2. 当前代码基线与缺口

本次检查的提交：Nuxt `c5bd9b2`、Rust `0261ffe3`、Flutter `448e2a51`、Go `f2a88662`。这里的提交是功能盘点起点，后续规划文档提交不改变该代码快照。

- Nuxt 是现存最新业务实现。`server/services/v2/` 有 auth、users、posts、groups、chat、media、notifications、presence、moderation 九个服务模块；另外必须检查 middleware、models、utils、plugins、storage、routes 及客户端调用。

- Nuxt 还存在 67 个 v1 路由文件，分布于 account/auth、analytics、follow、hashtags、interactions、notifications、system/test、tweets、users。旧路由可能是别名、独有能力或诊断入口，必须逐项分类，不能全部忽略或未经审查直接搬入公开 API。
- Rust `src/app/routes.rs` 只有独立健康接口与业务/文件代理接线，没有原生业务和 `/_ws`；`src/db/`、`cache/` 是可复用基础设施，不等同于已接线业务。
- Go 只有说明和契约副本，尚无 Go 服务。
- 四目录、契约快照和已有兼容运行记录已存在。它们证明第一阶段整理与打通，不证明三套原生功能一致。

## 3. 需求驱动的共同开发规则

需求正文和可执行验收规范必须语言无关。Nuxt 源码用于首次还原业务规则，之后三套后端都以同一份版本化需求为准；不能长期靠阅读 Nuxt 最新提交猜测如何迁移。

拟在主分支建立 `specifications/`，内容按功能分目录：

```text
specifications/
  requirements/       功能 ID、行为规则、权限、状态流转和兼容要求
  api/                HTTP、WS 事件、文件和鉴权契约
  database/           数据字典、共享事务/约束、迁移版本与事件约定
  scenarios/          语言无关的输入、前置条件、输出与副作用断言
  changes/            每次需求变更的三实现任务及兼容/发布顺序
  implementation/     Nuxt/Rust/Go 的版本、完成状态、用例和证据索引
```

这是一套待实现的文档/检查机制，目前 `contracts.mjs` 只验证既有契约副本，不能声称已经检查业务功能一致。

### 单项功能的必要内容

每项功能固定唯一 ID，写清输入/输出、鉴权/角色/所有权、字段缺省与 null/空值、排序分页、并发及幂等、事务边界、数据库/Redis/文件副作用、HTTP 错误和 WS 事件、依赖及失效处理。验收用例引用功能 ID；服务源码和测试引用同一 ID。需求修订保留来源与版本，不复用已删除功能的 ID。

实现状态分别使用 `not-started`、`in-progress`、`implemented`、`accepted`。Rust 的 Nuxt 代理另标 `proxy`，不可自动升为 `implemented`；Go 的无服务状态不能靠响应占位转绿。完成度不由路由存在、mock 返回或人工勾选单独决定。`accepted` 必须引用该版本真实测试证据、源码提交和运行模式。

### 新功能的同步流程

1. 先修改需求、公共契约与共同验收用例，形成一个变更 ID。
2. 变更清单必须同时列 Nuxt、Rust、Go 实现任务；影响前端时加 Nuxt Web/Flutter 任务，影响结构时加单一迁移任务。
3. 分别在固定工作区实现，每套提交记录同一变更 ID；不把三种语言源码整体互相合并。
4. 共享规范经显式工具生成各工程版本化副本，带源提交、版本、哈希；独立克隆只需自身副本即可编译。同步不搬移私有环境或运行数据。
5. 检查器拒绝缺失用例、过期规范、未列实现任务和无证据的验收状态；集成流水线检出精确的三分支提交运行共同场景。
6. 可保留开发中的局部进度，但该功能不能宣称“三后端已完成”或进入共同完成清单，直到三套验收一致。紧急修复若只先部署一套，需明确偏差、风险和追赶任务，不能静默遗忘其他实现。

Git 的三个分支无法靠一次普通提交同时更新；使用带三提交 SHA 的变更清单和完成检查协调。不以“文档更新会自动生成完整业务实现”作为承诺。文档提供稳定任务和验收依据，实际业务仍需分别编码。

## 4. 架构约束

- Nuxt 延续现有路由/service/model 边界；Rust 复用既有 Axum、Oracle/Redis 基础设施，按业务模块接入；Go 建立独立工程后选择经过驱动兼容性验证的实现。框架/驱动选择以 Windows/Linux、Oracle 19c/Free 兼容和可维护性试验为依据，不先堆依赖。
- 允许语言惯用组织方式，不要求逐行翻译 TypeScript；公开行为、数据语义与事件必须一致。防止为了复刻历史代码而复刻已确认缺陷：先在共同需求中修订，再对三套实现同一修复。
- 三套保持同一数据模型和 ID/序列规则，不各自新建不兼容表；签名/密码哈希、令牌轮换撤销、会话、验证码、邮件、Redis key/TTL、缓存失效和频道名称均写入共同规范，保证切换后端可继续读取同一业务。
- 结构升级始终单一权威和显式入口。现有 31 步迁移、checksum/ledger 和 DBMS_LOCK 语义保留；不要求 Rust/Go 运行 Nuxt Web 才能迁移。交付独立迁移工具/制品与共享迁移版本，业务进程不自动改表、不各自复制并执行不同 DDL。
- Rust/Go 原生处理上传、读取/范围请求/路径校验、媒体元数据与权限，以及认证 WS、订阅授权、Redis 跨实例投递、通知和在线状态；最终不能把 WS 或文件继续交给 Nuxt。
- 每套后端都具备明确的 API/WS/文件公共地址和代理信任规则；浏览器来源、Cookie/令牌、CORS、HTTPS/WSS 不能靠仅修改监听端口就默认成立，配置预检和实际矩阵需覆盖。
- 开发阶段可保留现有 Rust 兼容模式作回退，原生模式明确关闭该回退。原生验收主动阻断 Nuxt 上游连接，避免 catchall 或网关偷偷补齐缺口。

## 6. 验收方法

### 原生独立与功能一致

共同测试只配置目标后端和隔离资源，不允许目标实现依赖兄弟源码。Rust/Go 的 Nuxt 地址设置为不可达且禁用业务 fallback，启动时不启动 Nuxt；通过出站记录/拒绝上游连接验证，不仅检查一个环境开关。逐功能核对响应、权限和持久副作用；比较时只归一化随机 ID、时间等明确不稳定字段，不能忽略业务字段来制造相等。

交叉场景包括：Nuxt 写帖 Rust/Go 读、Rust 上传 Go/Nuxt 读、三实现轮换/撤销共享会话、跨实现群聊/私信/通知、缓存失效、共享序列与并发更新。为跨后端令牌轮换定义显式顺序，验证旧 refresh token 不能在另一实现继续使用。

### 新功能不会遗漏

以“给帖子新增一个可选字段”为同步演练：需求修订明确省略/空值/权限和数据库迁移；共同场景先失败；三后端分别实现；前端无需按后端类型分支。故意留下一个实现未完成，完成检查必须拒绝；全部实现通过并记录三提交后才允许变更完成。此例是机制验收，不要求为演示无故给产品添加字段，可在隔离测试夹具中实施。

### Git 与部署

固定 worktree 便于同时打开，不在已检出的分支之间强制切换；需要另一份快照时使用独立克隆或额外 worktree。保留原历史和美化分支归档结论，框架共享功能按来源迁入，不把 Flutter/Rust 的历史混合目录重新整包合并回主项目。

本地/混合/源码容器/镜像/外部依赖模式分别验证预检、启动、重复启动、日志、停止、重建保留数据。镜像未发布时必须有源码构建方式。另一台真实机器需验证外部浏览器可达的 HTTP/WS/文件地址、监听与防火墙、TLS 和持久化；容器不冒充另一台服务器。

## 7. 当前风险与边界

- 已确认的外部限制仍在：Oracle 19c 镜像授权和另一台真实机器尚不可用。它们阻碍最终对应验收，不阻碍本计划 P0–P6 的静态开发；不能因此把原生实现改回代理或放弃 Go。
- Flutter Windows C++ 工具链仍按用户此前选择暂缓；Flutter Web 可用于当前阶段。新计划不自动安装该工具链，也不声称桌面版验收通过。
- 现有恢复 ZIP 是前阶段已验证快照，不包含本计划后的原生开发，不能作为完整三后端交付。新发行需固定三实现提交、规范版本、迁移制品和共同验收记录后重新生成。
- Nuxt 既有缺陷、未测流程或模型服务 stub 必须在 P0 单列；相同功能不意味着复制安全缺陷，也不允许悄悄删除功能。涉及公开行为调整时先更新需求并记录兼容/迁移规则。
- 不给出未经依赖试验支持的工时承诺。以功能/场景和三实现验收状态衡量同步程度，不用代码行数、路由计数或编译成功代替。
