# Nuxt实时订阅生命周期实现断点

接续local-presence计划，不启动真实服务、不改分支或历史数据。当前生产_ws.ts仍等待全局Redis成功才登记，subscribedUsers/Chat/Global只有增加没有释放；presence走同步广播，没有发送前逐连接鉴权。两个客户端仍待后续接线。

1. 先实现可注入transport的连接级订阅控制器：同步创建本地能力，异步连接，确认目标频道后才connected；error/close/超时立即降级，至少1秒后重试；禁用适配器隐藏的自动重连/重订阅/命令重发。每次尝试有generation和AbortController，close释放定时器/连接，旧回调与旧promise不能恢复状态或派发。
2. 控制器只派发已声明/当前需要的频道，严格验证presence和控制帧边界；远程不能生成realtime_status。只过滤本实例presence，保留其他实例presence及未由本机本地投递的通知。合法通知保留原始JSON字符串，包括未配对UTF-16。
3. ioredis适配器独立于共享缓存/发布客户端的redisAvailable标志，沿用统一端口/TLS/密码配置。连接/命令各1.5秒；绑定错误/关闭回调，不打印原始异常、凭据或消息。
4. 集成时替换_ws.ts全局订阅集合，按已鉴权连接持有一个控制器；即时登记本地会话、欢迎帧与状态帧，不等待Redis。重连重新确认私有用户/presence和允许的其他频道。聊天join/leave须继续按现有权限规则，并将频道集合/重配置操作有界化；不得为完成presence而移除Nuxt已有聊天能力。
5. 统一wsSession发送队列：每连接16条，最多1024连接；presence、状态、通知和其他现有发送均经过当前会话核验。close/remove/积压/撤销释放控制器。保留原有欢迎、心跳、上线/离线延迟发布与Origin校验；关闭与鉴权期间返回的旧任务不能重新登记。
6. Nuxt现有通知/聊天先本地再Redis，不同于目前Go/Rust仅远程通知。不要直接过滤全部同server_id通知以冒充无重复：在连接内记录有界、短时的本地投递指纹，远程只去掉已经本地排队的同源回声；未本地发送的通知仍可送达。确切设计、共享语义与隔离回归须随接线确认，不能破坏私密通知隔离或丢失。
7. 用实际路由/会话管理器及可控transport测试降级、阻塞、失败重试、旧连接回调、同步订阅期间关闭、释放、鉴权撤销、超限和消息原文，再更新共同需求/WS任务/OpenAPI必要修订与三后端目标版本。只有当前source控制器通过测试，不代表生产路由已具备能力。

后续再接Nuxt Web/Flutter严格健康状态、unknown/降级反馈、身份/端点切换与恢复读取；完整业务/AI和Windows/Linux部署目标继续保留。

## 已完成的基础组件

realtime-subscription.ts和realtime-redis.ts已实现并通过隔离测试、Nuxt类型检查。共同presence/control向量、原始通知、generation/取消、确认超时、早到缓冲16、失败重试、频道增删/64上限、状态回调竞态和适配器心跳/清理均有覆盖；这些组件尚未被_ws.ts调用。旧路由/会话管理器测试通过，只说明旧行为未被这次未接线的组件改变，不能当新降级路由验收。

下一步从本计划第4至6项开始。先审通知本地回声指纹方案与现有publisher的实际字节、写入/鉴权顺序，再以真实路由隔离测试接线。源控制器已允许单连接最多64个聊天频道，但尚未影响产品；接线前须同步共同约束或按既有聊天接口规则调整。ioredis适配器只验证了配置透传和关闭隐藏重试，实际redis-config.ts对rediss/TLS与部署环境的解析仍需单独核验，不能把假客户端的tls字段透传当成真实TLS证明。
